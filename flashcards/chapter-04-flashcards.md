## Chapter 4: Inference Concepts: Serving Models at Scale — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Memory per parameter: FP16 vs FP8? | FP16 = 2 bytes/param; FP8 = 1 byte/param. Exam tip: halving precision roughly halves weight memory footprint. |
| 2 | Which GPU architecture introduced native FP8 support via the Transformer Engine? | NVIDIA Hopper (H100) and later generations. Exam tip: FP8 retains floating-point dynamic range, unlike INT8 integer quantization. |
| 3 | Dynamic batching vs continuous (in-flight) batching? | Dynamic batching (Triton) groups requests arriving within a time window into one fixed batch executed together. Continuous batching (e.g., TensorRT-LLM) lets new requests join an in-progress generation batch token-by-token. Exam tip: continuous batching improves GPU utilization for variable-length LLM generation. |
| 4 | Triton config field controlling max wait time to fill a batch? | dynamic_batching { max_queue_delay_microseconds }. Exam tip: trades a small latency increase for higher throughput. |
| 5 | What does the KV cache store, and why does it matter for memory? | Stores attention Key/Value tensors per generated token to avoid recomputation. Memory scales with batch_size × sequence_length × num_layers × num_heads × head_dim × 2 (K&V) × precision bytes. Exam tip: long contexts + large batches can exhaust memory even when weights fit. |
| 6 | NIM vs Triton Inference Server — when to use which? | NIM: pre-packaged, optimized single-model microservice with a standard API, minimal setup. Triton: general-purpose multi-framework server (PyTorch, ONNX, TensorRT) with custom batching, ensembles, and concurrent execution. Exam tip: NIM = fast deployment of supported models; Triton = flexible custom serving. |
| 7 | Effect of increasing batch size on latency vs throughput? | Larger batch size → higher throughput but typically higher per-request latency due to queuing. Exam tip: interactive apps need smaller batches/shorter queue delay; offline jobs favor large batches. |
| 8 | Which precision format is integer-based and requires calibration or QAT for accuracy? | INT8 (and INT4). Exam tip: integer formats need a quantization step unlike FP16/FP8, which are floating-point and generally deploy with less accuracy loss. |
| 9 | Training vs inference compute profile — key operational difference? | Training: forward + backward pass, large offline batches, higher precision, optimizer-state memory. Inference: forward pass only, variable/smaller batches, lower precision, no optimizer state. Exam tip: inference memory ≈ weights + activations + KV cache; training also needs gradients + optimizer states. |
| 10 | Triton feature enabling multiple model instances to run concurrently on GPU(s)? | instance_group configuration (concurrent model execution). Exam tip: more instances can raise throughput but consumes more GPU memory per instance. |
| 11 | Name backends supported by Triton Inference Server. | TensorRT, PyTorch (LibTorch), ONNX Runtime, Python backend, and others (e.g., vLLM backend). Exam tip: Triton is backend-agnostic — pick the backend matching the exported model format. |
| 12 | Why does quantization (e.g., FP16→INT8) reduce latency/memory but risk accuracy loss? | Lower bit-width reduces data moved/computed (faster, less memory) but reduces numerical precision, distorting sensitive weights/activations. Exam tip: scenarios balancing 'fits on smaller GPU' vs 'accuracy tolerance' usually point to INT8/FP8 when memory-constrained. |
